# Existing-project adoption techniques

Adoption is a state migration, not a bulk export.

1. Inventory the repository, runtime, active theme/plugins, content types,
   taxonomies/meta, Site Editor entities, blocks/patterns, media, ACF/extensions,
   publication/privacy classes, integrations, and verification channels.
2. Assign every surface exactly one ownership/disposition, provenance,
   compatibility result, dependency set, and reason. Unknown ownership blocks.
3. Review the generated managed-object manifest, stable identity map, adapter
   exceptions, and wave graph. Resolve identity collisions before baseline.
4. Rehearse backup restore and runtime installation on a disposable clone.
5. Capture the baseline from a fresh canonical read. Existing divergent Git
   files or locks are conflicts, not replace targets.
6. Select one public, low-risk, dependency-light canary. Complete snapshot,
   dry-run, CAS, canonical/editor/rendered verification, and rollback rehearsal.
7. Progress through bounded waves with checkpoints and a declared coexistence
   policy. Re-read each object before its apply.
8. Enable reviewed automation only after manual reconciliation is stable.
9. Retain source/backups until the separately approved de-enrolment criteria
   and recovery targets are met.

Inventory output is deterministic and redacted. Reports contain identities,
hashes, compatibility, classifications, counts, and evidence pointers—not
credentials or private payload bodies.
